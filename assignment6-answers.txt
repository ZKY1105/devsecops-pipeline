CI/CD Concepts 

CD vs. Deployment: 
Continuous Integration (CI) is the practice of automatically building and testing code changes whenever they are pushed to version control. 
Continuous Delivery (CD) automates the release process up to the point of staging/production readiness, meaning the software can be released at any time but requires a manual trigger or approval.

Continuous Deployment takes it a step further by automatically deploying every passing change directly to production without manual intervention.

Problems & solutions:
Untested broken code reaching main= Fixed by Automated Testing.
Exposed API keys/secrets committed to code- Fixed by Secret 
Scanning / Push Protection.Vulnerable dependencies going unnoticed= Fixed by Automated Dependency Scanning.
Lack of consistency/manual merging errors= Fixed by Automated CI/CD Workflows & Gates.

Pull Request vs. Push to Main ("Shift Left"): 

Running security checks on a pull request before merging catches vulnerabilities and bugs earlier in the development lifecycle ("shifting left") rather than discovering them after they are already merged into the production branch.

Definitions:
Workflow: A configurable automated process defined in YAML that runs one or more jobs.
Job: A set of steps executed on the same runner within a workflow.
Step: An individual task or shell command executed within a job.
Runner: A server (hosted or self-hosted) that executes workflows when triggered.
Action: A reusable, pre-packaged unit of code designed for use in workflows (e.g., actions/checkout@v4).

Local npm audit vs. Pipeline Scanning
Running npm audit locally depends on the developer remembering to run it, can be bypassed, and only checks their local machine state at that moment. A pipeline scan runs centrally and automatically on every single PR, enforcing mandatory organization-wide compliance before code can ever enter main.

Answer Task 2 Requirements 

I. Why npm ci over npm install? npm ci (Clean Install) installs dependencies strictly from package-lock.json, ensures a clean build environment by deleting node_modules first, and throws an error if lockfile discrepancies exist, making builds reproducible and reliable.

II. Why .github/workflows/? GitHub Actions specifically looks inside the .github/workflows directory in the repository root to discover and execute workflow configuration files.

Answers for Task 4


Task 4.1 (Difference between SCA and SAST):

SCA (Software Composition Analysis / Dependency Scanning): Analyzes third-party open-source libraries and dependencies (node_modules) for known security vulnerabilities and outdated versions (e.g., using npm audit).

SAST (Static Application Security Testing): Analyzes your custom source code and scripts for security flaws, insecure coding patterns, and logic vulnerabilities without executing the program.

Task 4.2 (Tool/Method used): npm audit integrated into the GitHub Actions CI pipeline to scan project dependencies automatically on every push.

Task 4.3 (Handling a vulnerability alert):

Review the advisory to see which package and version introduced the vulnerability.

Run npm update <package> or patch/upgrade the dependency version in package.json.

If no patch is available, evaluate if the vulnerable function is actually used, and apply mitigating controls or switch to an alternative package.

Task 4.4 (Why dependency scanning belongs in CI): Catching vulnerable packages automatically during CI prevents insecure code or compromised libraries from ever being merged into the main branch or deployed to production environments.

Answers for Task 5


Task 5.1 (Purpose of a security gate in a CI/CD pipeline): A security gate automatically evaluates code against predefined security criteria (like passing unit tests, zero critical vulnerabilities, or no hardcoded secrets) and halts the pipeline or blocks merging if a failure occurs, preventing insecure code from reaching production.

Task 5.2 (How branch protection rules enforce security): Branch protection enforces policies directly at the repository level—such as requiring pull requests and successful status checks from your CI pipeline—ensuring that developers cannot bypass automated security gates or push directly to main.

Task 5.3 (Why direct pushes to main are discouraged in DevSecOps): Direct pushes bypass peer code reviews, skip automated tests, and evade security scanning gates, introducing a high risk of regression, vulnerabilities, or unverified code entering the production environment.
